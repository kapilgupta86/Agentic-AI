How LLMs Actually Generate Text — And Every "Caching" Term, Finally Untangled

An LLM does not generate a sentence.

It generates one token. Then another. Then another. Each one runs the full machine from scratch: tokenize, embed, attend, predict, sample, repeat. What looks like "writing" is actually a loop running thousands of times per response.

That loop has two phases that behave nothing alike. Almost every optimization technique you've heard of — KV caching, prompt caching, prefix caching, semantic caching, quantization — only makes sense once you know which phase it's fixing. Confuse the phases, and you'll confuse the caches. So that's where we start.

The Two Phases Inference Actually Has

Prefill reads your entire prompt at once, in parallel. It's compute-bound — throw more GPU at it and it goes faster. This phase decides time-to-first-token: how long you wait before anything appears.

Decode generates the reply one token at a time, and each new token has to look back at every token that came before it. It's memory-bandwidth-bound, not compute-bound — the bottleneck is shuttling data around, not doing math. This phase decides tokens-per-second once the answer starts streaming.

Everything below is really just: which of these two phases does this technique speed up, and how? The map below shows the whole pipeline — and exactly where each kind of caching sits in it.

Layer 1: KV Cache — The Thing That Makes Decode Possible At All

During prefill, the model computes a key and a value vector for every input token — its "KV pairs." During decode, generating token #500 would normally mean re-running attention over all 499 tokens before it, from scratch, at every single step. The KV cache stores those key/value vectors so the model never recomputes them — it just appends the new token's KV pair and reuses everything else.

Think of it as the model's short-term memory for a single, in-progress answer. Without it, decode would be brutally slow — quadratically slower as the conversation grows.

It is not a feature you turn on or a product you buy — every LLM inference engine does this automatically, for every request, all the time. It doesn't persist between separate API calls. And it isn't free: the KV cache grows with every token in the context, which is exactly why long conversations get slower and heavier on memory. This growing footprint is the decode bottleneck — it's why quantizing the KV cache (storing it in INT8/INT4 instead of full precision) is a real lever people pull at scale.

Timing: lives and dies within one generation. Born at prefill, grows through decode, discarded when the response finishes.

Layer 2: Prompt Caching (a.k.a. Prefix Caching) — Reusing Prefill Across Requests

If your next request starts with the exact same prefix as a previous one — the same system prompt, the same tool definitions, the same reference document — why recompute that prefill work again? Prompt caching stores the KV computation from a previous request's prefix and reuses it on the next one.

The right analogy is a bookmark in a book. Instead of rereading from page one, the model jumps to the bookmark and only reads the new material.

The numbers are real: providers report 50–90% cost reduction and up to 80% latency reduction on cache hits, driven almost entirely through faster time-to-first-token. Generation speed (tokens/sec once decode starts) doesn't change at all — this is purely a prefill-side win.

Five mix-ups worth killing right now:

  • It is not response caching. Response caching replays an old answer verbatim. Prompt caching only reuses the input-side computation — the model still generates a fresh, unique reply every time.
  • It is not semantic caching (more on that below). It needs an exact, character-for-character prefix match. Change one token — a timestamp, a session ID, a reordered example — and the whole cache misses.
  • It does not modify the model. Zero weight changes. The model behaves identically whether the cache hits or misses; only the compute path is shorter.
  • It is not permanent. Caches are ephemeral — they expire after 5 minutes to 1 hour of inactivity depending on the provider.
  • It doesn't work below a minimum size. Every provider enforces a token threshold (roughly 1,024–2,048 tokens) below which caching simply doesn't activate.

Is "prefix caching" a different thing? No — same mechanism, different room. "Prompt caching" is the term hosted API providers use for the feature you control through their API. "Prefix caching" is the systems-engineering term for the same idea inside self-hosted inference engines, which often implement it automatically for any users sharing a prefix. If someone says "prefix caching," picture the serving engine's internals; if they say "prompt caching," picture the API knob you flip.

The structure that makes it work: static content first, dynamic content last. Tool definitions, system prompt, reference docs, and conversation history all get cached; your new message stays uncached and must come last. Anything dynamic buried in the middle — a timestamp, a randomized example order, a session ID — silently invalidates everything after it. This, not misconfiguration, is the number one way people accidentally kill their hit rate.

When to use it: multi-turn conversations, document Q&A/RAG over the same reference material, agentic loops with stable tool definitions, and batch jobs running one fixed instruction over many inputs. Rule of thumb: if more than half your input tokens repeat across requests, caching should be on.

When not to bother: prompts that change completely every call, requests spaced further apart than the cache window, prompts under the minimum token threshold, or true one-shot requests with no follow-up.

Timing: lives across multiple requests, but only for a short window (minutes to an hour) — a middle ground between the KV cache's single-generation lifespan and semantic caching's indefinite one.

Layer 3: Semantic Caching — Skipping Inference Completely

This one doesn't touch prefill or decode at all — it sits in front of the model. If a new query is semantically close enough (by embedding similarity) to a past query, the system returns the old stored answer and never calls the model.

It's not a speed optimization on generation — there is no generation on a hit. It's not exact-match — that's prompt caching's job. And it's not guaranteed-fresh — because it's replaying an old answer, it carries real staleness risk if the underlying facts have since changed.

The two work together, not against each other. Semantic caching catches genuinely repeated questions. Prompt caching reduces cost on everything else. This combination is sometimes called "double caching": semantic cache as the first gate, prompt cache as the fallback for whatever gets through.

Timing: operates before inference even starts, and can persist indefinitely — the longest-lived of the three.

Why These Terms Get Confused

They all sound like "the model remembering things," but they operate at completely different moments:

  • Semantic cache asks "have I seen a similar question before?" before inference starts, skips inference entirely on a hit, risks staleness, and lives indefinitely.
  • KV cache asks nothing — it's just bookkeeping during prefill and decode, always on with no cost knob, and lives for one generation only.
  • Prompt cache (= prefix cache) asks "have I seen this exact prefix before?" and skips prefill for the matching part, risks a miss if anything upstream shifts, and lives minutes to hours.

The Takeaway

An LLM's inference has two phases — prefill (parallel, reads your whole prompt at once) and decode (sequential, one token at a time). The KV cache is what makes decode possible at all, living for the duration of a single answer. Prompt caching (also called prefix caching, depending on whether you're talking to a hosted API or a serving engine) reuses that same prefill work across separate requests when the prefix matches exactly, for as long as the cache window stays warm. Semantic caching skips the model altogether when a new question is similar enough to an old one, trading a small staleness risk for the biggest possible savings. Three different problems, three different lifespans, one underlying idea: never make the model redo work it's already done.

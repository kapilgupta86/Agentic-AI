Optimizing L3 Semantic Caching: Selection Criteria, Vector Hygiene, and TTL Strategies

Architecting high-performance, cost-effective vector caching for modern LLM pipelines

A Layer 3 (Semantic) Cache sits in front of your LLM pipeline. Unlike exact-match prompt caching, it compares query embeddings using vector similarity (e.g., Cosine Distance). When an incoming prompt's vector is close enough to a past query (similarity score ≥ 0.88–0.92), it bypasses inference entirely and returns a stored response.

However, naïve implementations hit two massive production bottlenecks:

  1. Vector DB Bloat: Storing high-dimensional floating-point vectors (1,536+ dimensions) and large text responses for every query skyrockets memory costs, degrades search latency, and fills the index with "trash" queries that are never asked again.
  2. Thundering Herds & Stale Data: Sudden expiration of hot keys causes concurrent user requests to slam the LLM simultaneously, while background data changes lead to serving outdated facts.

To build an efficient L3 cache, you must combine strict Query Ingestion Criteria, Memory Hygiene Techniques, and a Soft vs. Hard TTL Architecture.

1. Selection Criteria: What Is Worth Caching?

A query should only enter your vector database if it satisfies three main evaluation gates:

A. High Compute Cost Threshold

  • Cache: High-latency RAG summaries, multi-step agent execution outputs, and heavy computational or code-generation tasks (high token counts, execution time > 3 seconds).
  • Skip: Fast, low-token completions (e.g., "Rephrase this in 5 words" or simple intent classification). The vector search overhead (10–30 ms) plus storage cost yields diminishing returns compared to a small, fast LLM call.

B. Public vs. Private (Generalizability)

  • Cache: Public FAQs, system usage instructions, and static knowledge-base queries with zero user-specific context ("How do I configure SSO?").
  • Skip: Queries with Personal Identifiable Information (PII), session IDs, or private state ("Summarize my order #9821 status").

C. Response Stability & Confidence

  • Cache: Deterministic, high-confidence outputs.
  • Skip: Model refusals ("I cannot assist with that"), 50x API error states, or responses containing heavy hedging ("I am not entirely sure, but...").

2. Preventing Vector DB Bloat & Index Fatigue

To keep the vector store lightweight and performant, route candidate prompts through a multi-tier write gate before indexing them:

  1. The "Write-on-Nth-Hit" Rule: Up to 80% of unique user queries are never repeated. Use a lightweight probabilistic structure (like a Redis Count-Min Sketch) to track query counts. Only generate a vector embedding and write to the database after a query has been seen at least N times (e.g., N ≥ 3) within a rolling window.
  2. Scalar Quantization (SQ8): Convert 32-bit floating-point vectors (f32) to 8-bit integers (int8). This compresses vector index memory usage by up to 75% with negligible loss in cosine similarity precision.
  3. Response Offloading: Store only the vector and payload metadata inside the vector index. Offload the full text response to a cheaper key-value or blob store (S3, DynamoDB, Redis String).
  4. Active Eviction (LRU & Low-Hit Purging): Enforce Least Recently Used (LRU) memory caps and run scheduled cleanup jobs to drop vectors that haven't registered hits over a set time window.

3. TTL Strategy: Soft TTL vs. Hard TTL

To handle background data updates without blocking users on multi-second LLM calls, decouple freshness (Soft TTL) from validity (Hard TTL) using an asynchronous Stale-While-Revalidate model.

Query Category TTL Strategy Typical Window Rationale
Security & Compliance Hard TTL Only 0 to 5 Mins Zero tolerance for staleness. Queries like "Account balance" or "GDPR rules" must force a hard miss upon expiration.
Volatile / Live Metrics Hard TTL Only 1 to 5 Mins Real-time queries ("Stock prices", "Flight status") invalidate quickly. Caching strictly absorbs short micro-bursts of traffic.
Knowledge Base & FAQs Soft + Hard TTL Soft: 1 Hour
Hard: 24 Hours		 Returning a 1-hour-old answer instantly preserves low p99 latency. An async background worker refreshes the answer out-of-band.
Heavy RAG Pipelines Soft + Hard TTL Soft: 30 Mins
Hard: 6 Hours		 Heavy summaries take 5–10s to generate. Soft hits return cached results immediately while workers update vector retrievals.
Static Concepts Hard TTL Only Infinite / LRU Fundamental facts ("Explain Transformer attention") never change. Keep until evicted by database memory limits.

4. Architectural Lookup Pipeline

Execution Flow

  1. Similarity Check: Compute vector similarity against stored prompts. If similarity < Threshold, execute the full LLM pipeline and write a new entry.
  2. If Similarity ≥ Threshold:
    • Hard Expired (Time > Hard TTL): Force a hard cache miss. Execute the LLM pipeline, update the cache, and return the new response.
    • Soft Expired (Soft TTL < Time ≤ Hard TTL): Instantly return the cached response to the user. Simultaneously, publish an asynchronous event (e.g., via Redis Streams or Celery) to re-run the query through the LLM and refresh the cache key.
    • Fresh (Time ≤ Soft TTL): Return the cached response immediately.

5. Production Guardrails

  • Distributed Worker Locking: To prevent dozens of soft-hit requests from triggering parallel background LLM calls for the same key, require background workers to acquire a distributed lock (e.g., Redis SET NX with a 30-second expiry). If a worker already holds the lock, subsequent soft-hits return stale data without queuing extra jobs.
  • Event-Driven CDC Invalidation: For dynamic databases, combine TTLs with Change Data Capture (CDC). When underlying source records change, issue an explicit metadata deletion call (e.g., DELETE WHERE category = 'pricing') to purge stale vectors immediately.

How LLMs generate text, and every caching term untangled

First published on keshavaai.in

An LLM does not generate a sentence. It generates one token. Then another. Then another. Each one runs the full machine again: tokenize, embed, attend, predict, sample, repeat. What looks like writing is a loop running thousands of times per response.

That loop has two phases that behave nothing alike. Almost every optimization you have heard of (KV caching, prompt caching, prefix caching, semantic caching, quantization) only makes sense once you know which phase it fixes. Confuse the phases and you will confuse the caches.

The two phases of inference

Prefill reads your entire prompt at once, in parallel. It is compute-bound: more GPU makes it faster. This phase decides time-to-first-token, the wait before anything appears.

Decode generates the reply one token at a time, and each new token has to look back at every token before it. It is memory-bandwidth-bound: the bottleneck is moving data, not doing maths. This phase decides tokens per second once the answer is streaming.

Everything below is one question: which of these two phases does this technique speed up, and how? The diagram at the top of this page shows where each kind of caching sits in the pipeline.

Layer 1: the KV cache, which makes decode possible

During prefill, the model computes a key and a value vector for every input token (its KV pairs). During decode, generating token 500 would otherwise mean re-running attention over the 499 tokens before it, at every step. The KV cache stores those vectors so the model only appends the new token's pair and reuses the rest.

Think of it as the model's short-term memory for one answer in progress. Without it, decode would slow down sharply as the conversation grows.

It is not a feature you switch on or a product you buy. Inference engines do this automatically on every request. It does not persist between separate API calls, and it is not free: it grows with every token of context, which is why long conversations get slower and heavier on memory. That growing footprint is why quantizing the KV cache (storing it in INT8 or INT4 instead of full precision) is a real lever at scale.

Lifetime: one generation. Created during prefill, grown through decode, discarded when the response ends.

Layer 2: prompt caching (also called prefix caching)

If your next request starts with exactly the same prefix as a previous one (the same system prompt, tool definitions or reference document), why redo that prefill work? Prompt caching keeps the KV computation for the prefix and reuses it. The analogy is a bookmark: instead of rereading from page one, the model resumes at the bookmark and reads only the new material.

Because the saving is on the input side, it shows up as lower cost and a faster time-to-first-token on long prompts. Generation speed once decode starts does not change, and output quality does not change either.

Five mix-ups worth clearing up:

  • It is not response caching. Response caching replays an old answer. Prompt caching reuses only input-side computation; the model still writes a fresh reply every time.
  • It is not semantic caching. It needs an exact match on the prefix. Change one token (a timestamp, a session ID, a reordered example) and everything after it misses.
  • It does not modify the model. No weights change. A hit and a miss give the same behaviour; only the compute path is shorter.
  • It is not permanent. Cached prefixes expire, from minutes to hours or longer depending on provider and setting (see the table below).
  • It has a minimum size. Providers set a minimum prompt length below which nothing is cached, and the minimum differs by provider and model.

Is "prefix caching" a different thing? Same mechanism, different room. "Prompt caching" is the name hosted API providers use for the feature you control through their API. "Prefix caching" is the systems term for the same idea inside a self-hosted serving engine, which can apply it automatically to any requests that share a prefix. In vLLM, for example, the cache is keyed on a hash of each block of tokens together with the tokens before it, so requests sharing a prefix share the stored blocks.

The structure that makes it work is static content first, dynamic content last: tool definitions, system prompt, reference documents and conversation history up front, and the new message at the end. Anything dynamic buried in the middle silently invalidates everything after it. This, more than misconfiguration, is the most common way people lose their hit rate.

Use it for: multi-turn conversations, question answering over the same reference material, agent loops with stable tool definitions, and batch jobs that run one fixed instruction over many inputs. A reasonable rule of thumb is that if more than half your input tokens repeat across requests, caching should be on.

Skip it for: prompts that change completely each call, requests spaced further apart than the cache lifetime, prompts under the minimum size, and one-shot requests with no follow-up.

What providers document (checked 14 October 2026)

  • Anthropic. Cache lifetime: 5 minutes by default, refreshed on use; 1 hour optional. Minimum prompt: 512 to 4,096 tokens, depending on model. Cached input price: Reads at 0.1x the base input price (0.05x or 0.025x on some newer models); writes at 1.25x (5 minutes) or 2x (1 hour).
  • OpenAI. Cache lifetime: Newest models: at least 30 minutes. Earlier models: in-memory, typically 5 to 10 minutes and up to 1 hour, or 24 hours. Minimum prompt: 1,024 tokens on the newest models; varies on earlier ones. Cached input price: Cached input discounted up to 95%; on the newest models, writes at 1.25x and reads at 0.1x.
  • Google Gemini. Cache lifetime: Implicit caching on by default for Gemini 2.5 and newer; lifetime not stated on the page. Minimum prompt: 2,048 to 4,096 tokens, depending on model. Cached input price: Savings passed on automatically; no percentage stated.

Sources: Anthropic prompt caching, OpenAI prompt caching, Google Gemini caching, vLLM automatic prefix caching. Prices and limits change often; check the provider's page before you rely on a number.

Neither Anthropic's nor OpenAI's page gives a general latency percentage, so treat any quoted figure for latency savings as workload-specific until you measure it on your own prompts.

A worked example of the write premium

Take a provider that charges 1.25x to write a 5-minute cache entry and 0.1x to read it (the Anthropic multipliers above). Count the cost of the shared prefix in units of its normal input price. Used once, caching costs 1.25 instead of 1.0, a small loss. Used twice, it costs 1.25 + 0.1 = 1.35 instead of 2.0. Used ten times within the window, it costs 1.25 + 9 x 0.1 = 2.15 instead of 10. This is arithmetic from the published multipliers, not a benchmark: your real saving depends on your hit rate and how much of each prompt is the shared prefix.

Lifetime: across requests, but only within the cache window. A middle ground between the KV cache (one generation) and a semantic cache (as long as you keep it).

Layer 3: semantic caching, skipping inference completely

This one touches neither prefill nor decode. It sits in front of the model. If a new query is close enough, by embedding similarity, to a past query, the system returns the stored answer and never calls the model.

It is not a speed-up for generation, because on a hit there is no generation. It is not exact-match; that is prompt caching's job. And it is not guaranteed fresh: it replays an old answer, so it carries a real risk of staleness if the underlying facts have changed. That is the trade: near-zero cost and latency on a hit, against an occasional stale answer.

The two work together. A semantic cache catches genuinely repeated questions; prompt caching cuts the cost of everything else that still shares context. Semantic cache first, prompt cache as the fallback is sometimes called double caching.

Lifetime: until a TTL, an eviction rule or an invalidation event removes the entry. You set the policy, so it can be minutes or months.

Why these terms get confused

They all sound like the model remembering things, but they act at different moments and live for different lengths of time.

  • Semantic cache. Asks: Have I seen a similar question?. Skips: All of inference, on a hit. Risk: Stale answers. Lives: Until your TTL or eviction rule removes it.
  • Prompt (prefix) cache. Asks: Have I seen this exact prefix?. Skips: Prefill for the matching part. Risk: A miss if anything upstream shifts. Lives: Minutes to hours.
  • KV cache. Asks: Nothing: it is bookkeeping. Skips: Recomputing attention at each step. Risk: Memory growth with context length. Lives: One generation.

Cost and speed cheat sheet

  • KV cache. Phase it helps: Decode. What it saves: Recomputing attention at every step. Turn it on when: Always on; nothing to configure.
  • Prompt / prefix caching. Phase it helps: Prefill. What it saves: Cost and time-to-first-token. Turn it on when: Prefixes repeat across requests, within the cache window.
  • Semantic caching. Phase it helps: Both (skipped entirely). What it saves: Cost and total latency. Turn it on when: Genuinely repeated questions, and some staleness is tolerable.
  • Quantization (not a cache). Phase it helps: Both, through memory footprint. What it saves: Memory, and some latency. Turn it on when: Almost always worth evaluating at scale.
  • FlashAttention (not a cache). Phase it helps: Both, through memory reads. What it saves: Latency. Turn it on when: Already standard in most modern serving stacks.
  • Speculative decoding (not a cache). Phase it helps: Decode. What it saves: Tokens per second. Turn it on when: High-volume, decode-bound workloads.

Takeaway

Inference has two phases: prefill, which reads the whole prompt in parallel, and decode, which writes one token at a time. The KV cache makes decode possible and lives for one answer. Prompt caching reuses prefill work across requests when the prefix matches exactly, for as long as the cache window lasts. Semantic caching skips the model when a new question is close enough to an old one, trading a staleness risk for the largest saving. Three problems, three lifetimes, one idea: do not make the model redo work it has already done.

Measure before you trust any of this. Cache hit rate, cost per successful task and answer freshness are the three numbers to watch; see cost-aware testing for how to test changes without a surprise bill.
